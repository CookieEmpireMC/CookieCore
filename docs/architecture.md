# Architecture

Maintained by the plugin-tester (Gandalf). Last updated: 2026-10-28 (`core-moderation-warns` review: `JdbcPunishmentStore` split, `/warn`, `/history` with `PunishmentHistory`, whisper block in `MuteListener`; `core-moderation-mutes` review: `MuteList`, chat listener, `PunishmentType.MUTE`; earlier: `core-moderation-bans` (`moderation` package, storage v3, login thread rule, `Messages` thread safety), `gamemode`, `scoreboard`, storage v2).

**Target:** Paper 26.3 (`26.3.build.205-stable`, pinned), Java 25, Maven, `api-version: '26.3'`. Same toolchain and rules as CookieClicker. Paper, Adventure/MiniMessage and the JDBC drivers (H2 2.5.252, MariaDB 3.5.10) are `provided`: nothing is shaded. The descriptor is `paper-plugin.yml` (no `plugin.yml`), with `loader: dev.casperrs.cookieCore.CookieCoreLoader`: that `PluginLoader` resolves the drivers listed in `cookiecore-libraries.properties` (pom-filtered, so `PluginDescriptorTest` ties them to `h2.version` / `mariadb.version`) through `MavenLibraryResolver.MAVEN_CENTRAL_DEFAULT_MIRROR`. The jar contains only `dev/casperrs/cookieCore/**` and the resource files.

CookieCore is the server's base layer. Gameplay lives in CookieClicker; Core never depends on it. Other plugins use Core only through `dev.casperrs.cookieCore.api` (`CookieCoreApi`, via Bukkit's `ServicesManager`). Everything else is internal.

Dependency direction (enforced, no cycles): `root -> {command, gamemode, moderation, player, scoreboard, sound, text, config, storage, api}`, `moderation -> {command, player, sound, storage, text, log, api, Perm}`, `command -> {player, scoreboard, sound, text, config, api, Perm}`, `gamemode -> {command, sound, text, Perm}`, `scoreboard -> {config, storage, text, log, api}`, `config -> {sound, text, storage}`, `player -> {storage, api}`, `log` and `storage` import nothing from Core, `api` imports nothing from Core outside itself. `config` must never import `scoreboard`. `Perm` is a constants leaf in the root package and exempt from the cycle check.
Known edge, not asserted: `text -> storage` (`Messages.banScreen` takes a `storage.BanRecord`). No cycle, because `storage` imports nothing from Core. Either keep it or pass a moderation-owned value (review L-6, 2026-10-27).

## Storage
Schema version 3 (`<prefix>schema_version`, default prefix `core_`):
- v1 (core-foundation): `<prefix>players(uuid PK, name, first_seen, last_seen)`.
- v2 (core-scoreboard): `<prefix>sidebar_prefs(uuid PK, visible BOOLEAN)`. A row exists only after a player changes the choice; no row means visible. A v1 database gains the table on start and keeps every player (tested).
- v3 (core-moderation-bans): `<prefix>punishments` (one row per kick, ban, tempban and unban target; never deleted): `id BIGINT AUTO_INCREMENT` PK, `type` (`KICK`, `BAN`), target and actor uuid and name (actor uuid NULL = console), `reason`, `created_at` and `expires_at` (epoch millis, NULL = permanent), `silent`, `active`, and the removal columns (`removed_at`, `removed_by_uuid`, `removed_by_name`, `remove_reason`). KICK and WARN rows are inserted inactive (WARN is history only, no column change, so no migration). A ban stays `active` after it expires (no cleanup task), so an unban marks every active row of the player. Index `<prefix>punishments_target (target_uuid, active)`. Tested: a v2 database upgrades in place and keeps its players; the store round trip, generated ids, expired-but-active rows and a corrupt row are tested on H2. MariaDB: by hand only (review 2026-10-27).
 Each migration is a list of statements run in one transaction together with the version bump (MariaDB auto-commits DDL, so every statement is `IF NOT EXISTS`). A database written by a newer plugin is refused. Migrations are append-only: a feature adds exactly one list to `Migrations.all`.

## Threading
- **Main thread:** Bukkit/Paper API, commands, messages, sounds, listeners, reload.
- **One IO thread** (`StorageThread`, daemon, `CookieCore-Storage`): every JDBC call, in order, one connection. Nothing else creates threads.
- **`PlayerDirectory`:** `byName` is a `ConcurrentSkipListMap` (lower-cased name, sorted) and `byId` a `ConcurrentHashMap`, both read without locks (commands, suggestions); writes (`seen`, warm-up merge, lookup merge) are `synchronized` together with the `live` set, so a live join is never overwritten by an older database row. `lookup(name)` answers from memory, else asks the IO thread and completes the future through the main-thread executor; if that executor or the IO executor refuses (plugin disabled, storage shut down) the future fails exceptionally instead of hanging.
- **Login thread** (`AsyncPlayerPreLoginEvent`, one per connecting player, concurrent): `ModerationListener` reads only `BanList` (`ConcurrentHashMap`, volatile `loaded`) and builds the screen with `Messages` (`yaml` volatile, `warned` concurrent, one shared `MiniMessage`) and `TimeText` (immutable formatter). No JDBC, no Bukkit main-thread call. `BanList` is written on the IO thread (start-up load) and on the main thread (commands); nothing else is written from login. A banned player's screen is the only per-login allocation.
- **History:** `/history` reads one page (`ORDER BY created_at DESC, id DESC LIMIT ? OFFSET ?`, page size + 1 to know whether a next page exists) on the IO thread and renders on the main thread. A page is an `int` offset, so very large page numbers overflow (review LOW, see the warns review).
- **Moderation writes:** a ban, unban, mute, unmute or warn runs its database write on the IO thread first; only on success does the main thread update `BanList` or `MuteList`, disconnect the target (bans), confirm and alert. A `busy` set (main thread only) refuses a second command on the same player while the first write is in flight.
- **Tab completion** (`knownPlayer`): `KnownPlayerArgument.listSuggestions` calls `PlayerDirectory#namesStartingWith(lowerCasePrefix, 200)`, a `subMap` range scan on the sorted map: O(log N + 200), measured about 5 to 15 microseconds from 10,000 to 500,000 known players (it was 18 ms to 800 ms as a stream over all names). `cachedPlayers()` is still a public read-only view but no production code uses it.
- No `Future.get()` / `CompletableFuture.join()` in production code (enforced).
- **Sidebar:** all Bukkit scoreboard calls on the main thread (`SidebarService`, `Sidebar`, `BoardSink`). `SidebarPreferences` reads a player's choice on the IO thread at join and answers on the main thread through the main executor; a change is remembered on the main thread at once and saved on the IO thread (IO queue is single-threaded, so a save always lands before a later read). The `visible` map is touched only on the main thread.
- If the database cannot be opened, Core logs once and runs memory-only (`storageAvailable()` false, joins are cached but not saved, `lookup` answers from memory).

## Sidebar (`scoreboard`)
- **Per player:** a `Scoreboard` of their own (never the main one), one `SIDEBAR` objective with `NumberFormat.blank()`, kept strongly while the player is a viewer and dropped on quit. The board is filled completely before `setScoreboard`, so nobody sees a half-built board.
- **Lines:** fixed entries `l00`..`l14` with unique descending scores (`n - i`, so the order is by score, never by name). A line changes only through `Score#customName`. Nothing is reset and re-added per refresh (that is what flickers). A line count change resizes the objective and rewrites every line; a title change rewrites the title only.
- **Diff:** `SidebarDiff` remembers what each viewer was sent and writes only the changes through `SidebarSink`, so a refresh with nothing new sends nothing. It is tested with a fake sink; `BoardSink` is the only Bukkit side.
- **One task:** `SidebarService` starts one repeating task (20 ticks) when the first viewer appears and cancels it when the last one leaves, toggles off or quits. `scoreboard.enabled: false` (reload too) hides everybody and runs nothing. On reload the layout is recompiled only when `scoreboard.yml` or the registered key set changed.
- **Values:** `scoreboard.yml` templates are parsed once (`CompiledLayout` / `Template`). Each refresh computes the values for the keys the layout uses only (built-ins `player`, `server`, `online`, `max`, `ping`, and registered keys); if they are equal to the last refresh the render is skipped. Text values are inserted as plain text and never parsed. A broken file keeps the last good layout on reload.
- **Replaced boards:** if another plugin gives a viewer a different scoreboard, Core drops that viewer and logs once. The player is left alone until they rejoin (no fight over the screen, at most one takeover per join). Core never calls `setScoreboard` on quit: the server already cleared the player.
- **Shutdown:** the plugin's disable hands every viewer the main scoreboard again and cancels the task. A placeholder owner's keys are removed when that plugin disables (`PluginDisableEvent`).
- **Toggle:** `/scoreboard toggle` (`/sb`) stores the choice through `SidebarPreferences` (memory first, IO thread saves). Default visible; a choice that cannot be saved lasts until the player leaves.
- **Placeholder registry:** `PlaceholderRegistry` implements the public `ScoreboardPlaceholders`. Keys match `[a-z0-9_]+`, may not be built-in, and may not be registered twice. Its `version()` changes on every add or remove, which is when templates are compiled again. Resolvers run on the main thread only for keys a layout uses. A resolver that throws or returns null shows empty text and logs once per key (`WarnOnce`).
- **Team fallback (not used):** if the in-game check shows `Score#customName` does not render with `NumberFormat.blank()`, swap only `BoardSink`: one `Team` per line with the fixed entry, `team.prefix` / `team.suffix` as the line text. `SidebarDiff`, `CompiledLayout` and the rest stay as they are.

## Enable / disable order
Before enable: Paper runs `CookieCoreLoader.classloader` (downloads the JDBC drivers from the Maven Central mirror; a missing or empty `cookiecore-libraries.properties` fails here). Enable (each step needs the one before): `ConfigLoader` (settings, messages, sounds; broken files fall back to the jar copy and are reported) -> `StorageThread` + `JdbcPlayerStore` -> `PlayerDirectory.start()` (migrate and warm the cache on the IO thread; enable does not wait for it) -> listeners (+ `seen` for players already online after a `/reload`) -> `ScoreboardModule` (`scoreboard.yml`, listeners, `apply()` for players already online) -> Brigadier registration (`LifecycleEvents.COMMANDS`) -> `CookieCoreApi` into the `ServicesManager`, last.

Disable (reverse; each step wrapped in `safely` so one throw never skips the next): the sidebar (`shutdown()`: every viewer back to the main scoreboard, task cancelled) -> unregister the API -> `directory.shutdown()` (queues `store.close()` behind the pending writes) -> `StorageThread.shutdown` (waits `CookieCore.SHUTDOWN_TIMEOUT_SECONDS`, 10, then drops what is left and logs it). Players still online get one last `seen` (refreshing `last_seen`) before the close is queued, in case Paper fires their quit events after plugins are disabled. `isEnabled()` is already false inside `onDisable`, so `runOnMainThread` throws `RejectedExecutionException` and `PlayerDirectory` fails the pending lookup future instead of dropping it. Residual: a task already handed to the Bukkit scheduler when the plugin is disabled is cancelled with it, so that one lookup future stays incomplete (review F-13, harmless at shutdown).

## Config, messages, sounds, permissions
- `config.yml`: `server.name`, `database.*` (`database.*` needs a restart; reload reports a change). `messages.yml`: MiniMessage, keys listed in `Messages.REQUIRED_KEYS` (the `command.*` keys; the `gamemode.`, `fly.` and `speed.` keys are checked by the message scan test instead, so a feature's keys can be added without touching the validator); defaults come from the jar copy so a key added in an update still resolves, and the admin is told which keys their file lacks. `sounds.yml`: event -> `key`, `fallback`, `volume`, `pitch-min/max`, `source`; contract events `ui_confirm`, `ui_error`, `ui_notify` are vanilla keys (Core ships no resource pack).
- Permissions are plain Bukkit nodes `cookiecore.<area>.<action>`, declared in `paper-plugin.yml` and as `Perm` constants; `cookiecore.admin.*` lists all admin nodes. `PluginDescriptorTest` keeps the three in sync.
- LuckPerms is an optional server dependency declared as `dependencies.server.LuckPerms` (`load: BEFORE`, `required: false`, `join-classpath: true`); it is not used yet, and its classes may only live in a `luckperms/` package (rule).
- `config.yml` holds only admin settings (`server.name`, `database.*`); every kept key has a default, so an old or partial file loads cleanly. Internal tuning is code constants.

## Rules (enforced by `ArchitectureRulesTest`, a source scan; run against a broken copy with `-Dcookiecore.mainSources=<dir>` to see it fail)
- No `playSound` / `Sound.sound` outside `sound/`; no `spawnParticle` anywhere (Core has no effects engine).
- No Bukkit/Paper/Adventure/Brigadier import in `storage/`, and `storage/` imports no other Core package; JDBC only in `storage/`.
- No player-facing text built or sent outside `text/` (`sendMessage`, `Component.text`, `MiniMessage`, `LiteralMessage`, kick, title, action bar, ...); message calls take a dotted key, never a sentence; `Placeholder.parsed` exists once (the prefix).
- No NMS, CraftBukkit, reflection into the server, WorldGuard (`com.sk89q`), legacy `ChatColor`/`§`, `PlayerLoginEvent`, `AsyncPlayerChatEvent`, `System.out`, `printStackTrace`, hardcoded world names.
- No `join()` / `Future.get()` / `Thread.sleep`; threads, executors and async tasks only in `StorageThread`; scheduler only in `CookieCore`.
- Scoreboard calls (`org.bukkit.scoreboard`, `setScoreboard(`, `getScore(`, `registerNewObjective(`, `getNewScoreboard(`) only in `scoreboard/`.
- `api/` imports only `java.*`, itself, and `Player`, `Plugin`, `Component` (relaxed on 2026-10-27 because `ScoreboardPlaceholders#register(Plugin, String, Function<Player, Component>)` is the contracted surface; any other Paper or Adventure type still fails the rule); no mutable static fields; no static collections of Bukkit objects; `net.luckperms` only in `luckperms/`; no package cycles.
- Tests (not source scan): `paper-plugin.yml` <-> `Perm` <-> `pom.xml` <-> `cookiecore-libraries.properties` (via `CookieCoreLoader.libraries()`) agree; `sounds.yml` contains every `SoundEvents` constant; every message parses with a strict MiniMessage and every message key used in code exists.
- Known one-way dependency, not asserted: `config` imports `sound` (`SoundConfigParser`), `storage` (`DatabaseSettings`) and `text`. It is not a cycle (nothing imports `config` back). Follow-up: move `DatabaseSettings` out of `storage` or assert the direction once it is settled.

## Standards (short form of the team rules, shared with every repo)
- **Comments:** only what the code cannot say: a non-obvious *why* (version quirks, client behaviour, thread rules, maths), public API contracts, format notes in files admins edit. No comments that repeat the code, narrate history ("since", "was", brief or finding IDs) or describe the obvious. Javadoc is 1-2 lines where needed, with **no `@param` / `@return` tags**: units, ranges and special values (ticks, `0 = off`, what `null` means) go in one doc line or in the parameter name.
- **Structure:** packages by feature (sub-packages once a package passes about 25 classes); one responsibility per class; classes under about 500 lines and methods under about 60; shared helpers instead of copies; no wildcard imports; no package cycles; `config` imports no feature package (today's exception is listed above).
- **Types:** records and `final` fields by default; `@Nullable` or `Optional` on purpose, never a silent `null` return.
- **Config:** `config.yml` holds only admin settings (resource pack first, database, feature switches, distances, debug). Every kept key has a built-in default. Balance values stay in `buildings.yml` / `upgrades.yml`, sounds in `sounds.yml`, effects in `effects.yml`.
- **Performance:** nothing per tick or per click that parses, allocates or queries more than it must; repeating tasks start on demand and stop when idle; saves are batched off the main thread and skip unchanged rows, but quit and shutdown always write; async only for pure work (maths, serialization, JDBC), after a spark profile shows it matters.
- **Descriptor:** `paper-plugin.yml` (no `plugin.yml`); JDBC drivers through a `PluginLoader` on `MavenLibraryResolver.MAVEN_CENTRAL_DEFAULT_MIRROR`, versions from a pom-filtered properties file tied to the pom by a test; plugins we call under `dependencies.server` with `load`, `required`, `join-classpath`; commands via Brigadier `LifecycleEvents.COMMANDS`; permissions declared in the descriptor and tested against `Perm`. Paper plugins are still experimental: re-test a first start on every Paper bump.
